# Java TLS Certificate Problems

## Symptom

A JVM build (Gradle, Maven, the IntelliJ Plugin Verifier, …) cannot download anything:

```
javax.net.ssl.SSLHandshakeException: (certificate_unknown) PKIX path building failed:
sun.security.provider.certpath.SunCertPathBuilderException:
unable to find valid certification path to requested target
```

Typical secondary symptoms, all of them the *same* root cause:

- `Could not resolve all dependencies for configuration ':plugin:compileClasspath'`
- `Could not determine the dependencies of task ':plugin:verifyPlugin'`
- `failed to compute value with custom source 'ProductReleasesListingValueSource'`
- A confusing configuration-cache error that mentions
  `Unable to make field private java.security.cert.X509Certificate
  sun.security.validator.ValidatorException.cert accessible` — this is Gradle failing to
  *serialise* the TLS exception, not a separate problem.

`--offline` does not help unless the artifact already sits in the local cache.

## Cause

Something between the JVM and the server terminates TLS and re-issues the certificate with its
own root CA: a corporate proxy (Zscaler, Netskope, …) or a consumer antivirus with "web/SSL
scanning" (Norton, Kaspersky, ESET, Avast, Bitdefender). The browser works because Windows/macOS
trusts that root; the JVM does not, because it ships its **own** truststore (`cacerts`).

## Fix

### 1. Identify the interceptor

```bash
openssl s_client -showcerts -connect repo.maven.apache.org:443 \
  -servername repo.maven.apache.org </dev/null 2>/dev/null \
  | grep -E "^ *[0-9]+ s:|^ *i:"
```

The `i:` (issuer) line names the interceptor, e.g.
`i:OU=generated by Norton Antivirus for SSL/TLS scanning, O=Norton Web/Mail Shield, CN=Norton Web/Mail Shield Root`.
If the issuer is a real public CA (DigiCert, Let's Encrypt, …), the cause is something else —
stop here.

### 2. Find the JDK the build actually uses

Do not guess — the build may use a different JDK than `java -version` on the PATH:

```bash
./gradlew -version --console=plain   # look at "Daemon JVM"
```

### 3. Export the root CA

The root is already trusted by the OS, so take it from there.

**Windows** (PowerShell — no elevation needed for the export):

```powershell
Get-ChildItem -Path Cert:\LocalMachine\Root, Cert:\CurrentUser\Root -ErrorAction SilentlyContinue |
  Where-Object { $_.Subject -like "*<interceptor name>*" } |
  Select-Object PSParentPath, Subject, Thumbprint, NotAfter | Format-List

$cert = Get-Item "Cert:\LocalMachine\Root\<THUMBPRINT>"
[System.IO.File]::WriteAllBytes("<scratchpad>\root.cer", $cert.Export('Cert'))
```

`WriteAllBytes` does **not** create directories — `New-Item -ItemType Directory -Force` the
target first or it fails with `DirectoryNotFoundException`.

**macOS**: `security find-certificate -a -c "<name>" -p /Library/Keychains/System.keychain > root.pem`

**Linux**: the root usually already sits in `/usr/local/share/ca-certificates/`.

### 4. Back up `cacerts`, then import

Always back it up first — a damaged truststore breaks every JVM tool on the machine.

```powershell
Copy-Item "<jdk>\lib\security\cacerts" "<scratchpad>\cacerts.backup" -Force
```

```powershell
& "<jdk>\bin\keytool.exe" -importcert -noprompt -cacerts -storepass changeit `
    -alias <interceptor-slug>-root -file "<scratchpad>\root.cer"
```

Notes:

- `-cacerts` targets the JDK's default truststore; the default password is `changeit`.
- Check `Get-Acl "<jdk>\lib\security\cacerts"`. A JDK under the user profile
  (`C:\Users\<user>\.jdks\…`, SDKMAN, Toolbox) needs **no** elevation. A JDK under
  `C:\Program Files` does — write the commands to a script file and run
  `Start-Process -Verb RunAs -Wait`.
- Repeat for every JDK involved (build JDK, IDE JDK, a separate toolchain JDK).

### 5. Restart the daemon — this step is easy to miss

A running Gradle daemon keeps the old truststore in memory, so the very next build fails
**identically** and it looks like the import did not work:

```bash
./gradlew --stop
```

Then re-run. Verify against the real thing (a task that downloads), not just `-version`.

## Alternatives, when the truststore must not be touched

1. Point the JVM at a separate truststore that contains the root:
   `GRADLE_OPTS="-Djavax.net.ssl.trustStore=<path> -Djavax.net.ssl.trustStorePassword=<pw>"`.
2. On Windows, `-Djavax.net.ssl.trustStoreType=WINDOWS-ROOT` makes the JVM use the OS store
   directly (works for reading, but not with every tool).
3. Run the affected task in CI, where the interception is absent.

Never disable certificate validation, and never tell the user to.

## Reporting

State plainly what was changed and where the backup is — modifying a JDK truststore is a
machine-wide change that outlives the session.
